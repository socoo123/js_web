## 1. 先分清谁安装，谁执行

运行时执行 JS 并提供宿主 API，包管理器解析、安装、锁定依赖。Node 是运行时；npm、Yarn、pnpm 是包管理器；Bun 同时提供运行时、包管理、测试和构建等命令，需按子命令判断职责。

**先猜一猜：** package scripts 写着 node src/cli/report.js，经 pnpm run report 执行时，运行时会变为 pnpm 吗？

不会，仍是 Node。上方对照卡的纯规则输出应保持 52，依赖布局不能改变同一组业务输入的统计。

在工作区执行：

```sh
npm run lab -- experiment managers
```

工具在 .lab/sandboxes/managers-* 下创建 npm 与 pnpm 两个副本，仅复制你当前的 core、cli、data；各声明同一 semver 依赖。终端打印目录、安装日志、6/52/2634800 报告与实际解析路径。pnpm 通过固定版本的临时调用准备，不修改全局安装或主清单。

<a id="2-yarn先认版本再认安装方式"></a>

## 2. Yarn 要先认两代与链接方式

Yarn Classic 指 1.x，Modern 指后续版本线。Modern 常用 PnP，以 .pnp.cjs 记录依赖解析，不一定生成传统 node_modules；也可以按项目配置使用 node-modules linker。旧教程中“没有 node_modules 就没安装成功”不适用于所有方式。

Corepack 管项目选择的包管理器版本，与依赖锁分工不同；是否预装取决于 Node 发行版与环境，先检查实际命令，不把它当永久内置事实。现代 Yarn 官方安装路径使用 Corepack，本课程实验不要求更改全局工具。

workspaces 用于同仓库多个包的关系，peerDependencies 表达消费者需提供的宿主依赖；例如插件常要求兼容的 React。它们不是复制一份依赖目录的同义词。[Yarn PnP](https://yarnpkg.com/features/pnp)。

<a id="3-pnpm共享存储按依赖关系建立链接"></a>

## 3. pnpm 的存储与解析路径

pnpm 使用内容寻址存储，并按依赖关系组织链接。实验中 semver 的真实路径经过 node_modules/.pnpm；npm 的布局通常更扁平。硬链接/符号链接与 PnP 都在改变安装和解析，不改变 JavaScript 的模块语法。

**先猜一猜：** 某包出现在磁盘或传递依赖树中，就能在自己的业务模块直接 import 吗？

业务直接使用的包应在本包清单显式声明。提升或祖先目录可能让未声明依赖偶然可解析，换环境便失效；严格解析策略更容易暴露问题。

在两个副本内查看 package.json 和 semver 的打印路径。记录 npm 的 package-lock.json 与 pnpm 的 pnpm-lock.yaml，检查主工作区没有新增其他管理器锁。

<a id="4-bun同一个命令名承担多种职责"></a>

## 4. Bun 的多个职责分别验证

Bun 运行时使用 JavaScriptCore，Node 使用 V8。bun install 安装包，bun run 分发脚本，bun test 运行测试，bun build 构建。若脚本明确调用 node，不能仅凭外层命令名认定已切换运行时；需要看具体选项和实际 process 信息。

Bun 提供许多 Node 兼容 API，但兼容性要落到项目使用的 fs、stream、模块解析与原生扩展。能跑一个算术例子不足以证明应用兼容；选择时比较当前项目的测试结果、团队约定和工具生态。[Bun 的 Node 兼容说明](https://bun.com/docs/runtime/nodejs-apis)。

本次必做比较已经包含两种包管理器，无需为了认识地图装遍所有工具。把实际结果写在 notes/tooling.md：版本、报表、锁名、解析路径、运行时、主锁检查，以及团队选择理由。

## 常见错误与调试

1. **现象与触发**：在打印出的 pnpm 副本中，从 package.json 删除 semver 声明，再执行安装并尝试解析 semver。
2. **工具**：对照清单、安装树和终端打印的绝对解析路径；可在该副本运行 node --input-type=module -e 'console.log(import.meta.resolve("semver"))'。
3. **证据**：清单未声明该包；解析可能失败，也可能退到上级工作区的 node_modules，已不再使用副本自己的依赖。
4. **原因**：代码依赖了清单之外的安装布局。
5. **修复**：在此隔离副本显式恢复 semver 的固定声明并安装，不通过放宽全局提升规则掩盖。
6. **确认**：解析回到副本局部路径，两个报告一致，主锁和主源码没有变化。若尝试 Bun，另记录运行时与 API 检查，不能沿用 Node 结果。

## 小结

- 运行时、安装、脚本、测试与构建分别判断。
- Yarn 两代与 PnP、pnpm 链接采用不同解析布局。
