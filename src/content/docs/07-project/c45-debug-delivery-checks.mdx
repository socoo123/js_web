## Java 程序员先看这里

Java 的堆栈、断点、请求链和 GC 经验仍能用。浏览器多了 HTML、模块、CSS、DOM、存储和 React 缓存这些边界：先判断哪一层失败，再挑面板。这里没有与 DevTools 一一对应的 Java API，不需要另写一套界面来类比。

## 1. 先确认失败的是哪一种资源

<a id="url-从域名根还是应用目录开始"></a>

Network 里的真实 URL 比“应该加载这个文件”更有用。在 `src/react/index.html` 找到加载 `main.jsx` 的 script，把文件名暂时拼成 `mian.jsx`，保存并刷新。

预期：页面不再出现商品，Network 有失败的模块请求。F12 → Network，勾选 Disable cache，刷新后点失败项，依次看 **Headers → Request URL、Response、Initiator**。修复是把源码里的文件名改回去，而不是清缓存。

**先猜一猜：** 页面位于嵌套演示目录时，两个路径会请求同一个地方吗？在 Console 执行：

```js
const deliveryPage = "https://socoo123.github.io/js_web/demos/inventory/";
console.log(new URL("/products.json", deliveryPage).pathname);
console.log(new URL("products.json", deliveryPage).pathname);
// → /products.json
// → /js_web/demos/inventory/products.json
```

第一条从域名根解析，第二条从当前目录解析。构建时的 public base 和运行时拼接 URL 要分别检查。Java 的 context path 经验能帮助理解前缀，但浏览器仍按 [URL 规则](https://developer.mozilla.org/en-US/docs/Web/API/URL_API/Resolving_relative_references)解析每一个地址。

<a id="404断网错误正文分别判断"></a>

| 证据 | 已经知道什么 | 下一步 |
| --- | --- | --- |
| 模块请求 404 | 文件路径没有对应资源 | 查 HTML 引用和构建前缀 |
| HTTP 200，但 Response 是 HTML | 返回的不是预期 JS/JSON | 查服务器是否回退到首页 |
| `(failed)`、Failed to fetch | 没拿到可用 HTTP 响应 | 结合 Console 查断网、连接或浏览器策略 |
| 没有 HTTP 请求，但界面显示模拟读取失败 | 可能走浏览器内 repository | 看 Sources 的调用链与 Query 状态 |

C32 以后，主应用详情走浏览器内 mock repository，不发送商品 GET。点“模拟详情失败”再“重试详情”，应该先报错再恢复；Network 没有商品请求是这条链的正常表现。用 Offline 可以检查模块加载失败，不能用它证明内存 repository 的网络重试。

## 2. 事件执行了，React 仍需要新的状态

读取结果不是新的写入口。`InventoryView` 从 `useInventory()` 取得 Query 的商品投影；正式更新仍走 `dispatch → repository → 查询失效 → 重新读取`。

在 `src/react/App.jsx` 找到 `async function restock(id, amount)`，暂时把整个函数换成下面的错误版本。保留其他函数：

```js
// 有问题的写法：只改读取结果，没有提交正式更新
async function restock(id, amount) {
  products.find((product) => product.id === id).stock += amount;
}
```

刷新到初始 P001=12，点它的“立即补一件”。预期：界面仍为 12。对象字段可以在 Sources 里变成 13，但没有 repository 写入和缓存通知；后续无关渲染还可能把污染显露出来。

修复时恢复原来的异步更新链：

```js
async function restock(id, amount) {
  try { await dispatch({ type: "restocked", id, amount }); setOperationMessage(""); }
  catch (error) { setOperationMessage(error.message); }
}
```

预期：一次点击后 P001=13，总库存 53、价值 2674700 分；P004 仍为 3。repository 校验并持久化，Query 重新读取，列表与派生汇总一起变化。Java 字段赋值会改变对象；React 还需要约定好的更新与通知边界。

**先猜一猜：** 新数组一定意味着商品也都是新对象吗？

```js
const originalRows = [{ id: "P004", stock: 3 }];
const copiedRows = [...originalRows];
console.log(originalRows === copiedRows); // → false
console.log(originalRows[0] === copiedRows[0]); // → true
```

数组展开复制的是槽位，里面的引用仍共享。修复时应沿被修改路径创建新对象，而不是仅换容器。Java 的 `new ArrayList<>(rows)` 也不复制内部商品。

## 3. 布局看尺寸，恢复看存储原文

<a id="从溢出的元素反查-css"></a>

`src/react/main.jsx` 已导入 `src/vanilla/styles.css`。在这份 CSS 末尾暂时加一条：

```css
/* 有问题的写法：窄屏无法满足最小宽度 */
main { min-width: 44rem; }
```

把设备工具栏宽度设为 360。Elements 选中 main → Computed 看 min-width 和实际 width，回 Styles 找到这条规则。删除刚加的声明并保存源码，按钮应回到视口内；不要用 `body { overflow-x: hidden }` 把操作裁掉。Java 布局管理器的约束也影响尺寸，浏览器还要结合层叠、盒模型与最小内容宽度。

<a id="存储损坏时先保留现场"></a>

存储排错先保护原文。在当前页面点“保存本地快照”，再把下列内容保存为临时文件 `invalid.json`，用“导入快照”选择它：

```json
{"version":1,"products":[{"stock":""}]}
```

预期：显示“快照操作失败”，当前商品不变。Application → Storage → Local Storage 中比较导入前后的 `js_web:inventory:react:v2` 及 `:backup`，原文应逐字不变。JSON 语法合法，只说明可以解析；字段仍需业务校验。Java 读取外部 DTO 时同样要先验证再保存。

要练习损坏恢复，先确认有有效备份并导出快照，再只把上述**库存主键**的值改为坏 JSON。点“恢复备份”，确认有效库存回来，坏原文保存在 `:damaged`。不要清空整个 origin；网站学习进度是另一组键。同协议、主机和端口下的不同路径共享 localStorage。

## 5. 最后检查性能、内存与操作可达性

<a id="performance-看一段操作的时间花在哪里"></a>
<a id="memory-找到谁还保留着对象"></a>

> 未运行验证：下面的 DevTools 图形界面 Performance 录制与 Heap snapshot 人工分析，请在自己的 Chrome 按步骤完成。

Performance 先录制首次展开“查看分类报表”，再录制收起后重新展开；保持视口和节流一致。Network 看首次按需模块请求，Performance 的 Main、Bottom-up 看脚本、布局和绘制；记录实际调用与时间分布，不规定跨机器的毫秒阈值。Java 性能分析也先找热点，而不是先加缓存。

Memory 则看保留引用。在 `src/react/useInventoryShortcuts.js` 暂时注释掉移除 keydown 监听器的 return 行；切换分类数次，Effect 每次收到新的 onRestock 回调。对比修复前后相同次数的操作：Memory → Heap snapshot → Comparison，沿 Retainers 检查 window 监听器是否仍保留旧回调。恢复那一行后重新加载、按相同次数重做。

预期：正确实现每次清理旧监听器，只保留当前订阅。单张堆快照或堆大小上升不等于泄漏；调试工具自己也可能保留对象。自动行为检查与监听器观察是证据，最终解释要对应真实保留链。

## 常见错误与调试

<a id="补货点了数字一直停在-12"></a>

**现象**：使用第2节故障版本，点击补货后数字仍12，Console无异常。**工具**：Sources 在直接改 stock 的行设断点；Components 查看 InventoryView 与 Provider 的数据，沿 Call Stack 回到按钮事件。

**证据**：事件命中、字段已13，但 dispatch没有执行、repository未保存；页面仍12。**原因**：把只读投影当成另一份可写数据源。**修复**：恢复第2节的 dispatch函数。**确认**：从相同起点点击得到13/53，再运行本课检查；只断言字段变13会漏掉这个故障，必须断言用户看到的结果。

## 小结

- 资源、状态、存储和布局分别收证，再串起调用链。
- repository是正式写入口，Query读取结果不能原地修改。
- 生产断点需要同次JS与map；性能看操作，内存看引用链。
- 自动检查、手工采样与自己的解释各有职责。

自测：模块404先查哪里？没有商品GET为什么详情还能读取？字段13而页面12说明哪段没完成？怎样证明坏导入保住旧快照？下一课把这份应用按严格静态路径交付。
