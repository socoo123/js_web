本课选五项交付风险，其中一项是接上后端才有的：服务器拒绝了保存，用户却不知道该改哪里。检查由Vitest、RTL和真实浏览器分工完成；测试文件数、截图数、快照断言数都不是“理解了多少”的分数。

## Java 程序员先看这里

JUnit的Arrange/Act/Assert与分层经验可以直接迁移。Vitest是运行器，RTL帮助渲染和查询界面，user-event驱动交互，Playwright运行真实浏览器；由谁启动测试，不决定测试范围。既有项目也常用Jest，本项目不维护两套重复运行器。让repository抛出 `ApiError`，相当于用Mockito让DAO抛异常；连真实后端的那条流程，相当于带测试数据库的Spring集成测试。

## 2. 核心规则先在Node测，断言业务结果

<a id="2-核心规则先在-node-测断言业务结果"></a>

新建 `tests/react/regression.test.jsx`。下面几段按顺序组成完整文件。第一段是导入；沿用C35的support，它提供DOM清理、断言扩展和独立内存repository。`vi`、`within` 和 `ApiError` 留给第3节的后端错误测试。

```jsx
// @vitest-environment happy-dom
import React from "react";
import { expect, test, vi } from "vitest";
import { render, screen, waitFor, within } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { freshRepository } from "./support.jsx";
import { saveProducts, storageKey } from "../../src/services/storage.js";
import { ApiError } from "../../src/services/api-repository.js";
import App from "../../src/react/App.jsx";
import seed from "../../data/products.json";
```

紧接导入，加入第一条测试。这个Map只替代存储介质，实际执行项目的saveProducts、编码和业务校验：

```jsx
test("非法保存抛错以后，主快照与备份原文都不变", () => {
  const records = new Map();
  const storage = { getItem: (key) => records.get(key) ?? null, setItem: (key, raw) => records.set(key, raw) };
  saveProducts(storage, seed);
  saveProducts(storage, seed);
  const before = new Map(records);
  const invalid = seed.map((product) => product.id === "P004" ? { ...product, stock: "8" } : product);
  expect(() => saveProducts(storage, invalid)).toThrow();
  expect(records.get(storageKey)).toBe(before.get(storageKey));
  expect(records).toEqual(before);
});
```

预期：通过。两次合法保存建立主键与backup，再写入字符串库存。既检查异常，也检查完整副作用；只验证throw会遗漏“先覆盖再报错”。期望值来自保存前的原文，不调用被测函数重新计算expected。Java单测也是检查契约，而不是复制实现。

这条测试虽然放在React测试目录，测的仍是函数边界；happy-dom不是它的核心依赖。保存/恢复涉及repository的完整流程，已有 `review.test.jsx` 继续覆盖。

## 3. RTL测用户操作，保留真实表单与请求校验

<a id="3-rtl-测用户操作保留真实表单与请求校验"></a>

在同一文件末尾加入第二条测试。从真实App和可访问名称开始，逐字输入而不是直接设置一整串值：

```jsx
test("连续输入保留完整条件，清空后回到原库存", async () => {
  const user = userEvent.setup();
  render(<App inventoryRepository={freshRepository()} />);
  await screen.findByRole("heading", { name: "P001 机械键盘", exact: true });
  const search = screen.getByRole("textbox", { name: "搜索", exact: true });
  await user.type(search, "P004");
  expect(search).toHaveValue("P004");
  expect(screen.getAllByRole("article")).toHaveLength(1);
  expect(screen.getByRole("heading", { name: "P004 USB-C 扩展坞", exact: true })).toBeInTheDocument();
  await user.clear(search);
  await waitFor(() => expect(screen.getAllByRole("article")).toHaveLength(6));
  expect(screen.getByText("库存 52 / 价值 2634800 分")).toBeInTheDocument();
});
```

预期：完整文本P004，只有扩展坞；清空后恢复六件与原始汇总。`await user...` 等待一次交互，`findBy` 等待异步元素，`waitFor`等待条件；不靠固定sleep让错误“消失”。Java对象集成测试的经验仍能用，但这里的结果是DOM和用户能读到的内容。

<a id="请求替身放在哪里决定测到了什么"></a>

后端拒绝这一项新增两条。替身放在repository边界：`vi.spyOn(repository, "save")` 只让第一次保存抛出 `ApiError`，真实的App、编辑器、Provider和Query都参与。先加一个打开编辑器的小函数和422这条：

> 未运行验证：本节的三条后端错误测试还没有在本课的工作区里运行。请按步骤自己尝试。

```jsx
async function openEditor(repository, id) {
  const user = userEvent.setup();
  render(<App inventoryRepository={repository} />);
  await user.click(await screen.findByRole("button", { name: `编辑 ${id}`, exact: true }));
  return { user, form: screen.getByRole("form", { name: "商品编辑", exact: true }) };
}
test("后端 422 的字段错误落到对应输入框，草稿与库存不变", async () => {
  const repository = freshRepository();
  vi.spyOn(repository, "save").mockRejectedValueOnce(new ApiError(422,
    { code: "VALIDATION", message: "商品字段不合法", fields: { priceCents: "价格必须是非负安全整数分" } }));
  const { user, form } = await openEditor(repository, "P004");
  await user.click(within(form).getByRole("button", { name: "保存", exact: true }));
  const price = within(form).getByLabelText("价格（元）", { exact: true });
  await waitFor(() => expect(price).toHaveAccessibleDescription("价格必须是非负安全整数分"));
  expect(price).toHaveAttribute("aria-invalid", "true");
  expect(price).toHaveFocus();
  expect(screen.getByText("库存 52 / 价值 2634800 分")).toBeInTheDocument();
});
```

预期：价格输入框的可访问说明就是服务器给的消息，`aria-invalid` 为true，焦点在它上面，汇总仍52。用可访问说明断言，是因为读屏软件读的也是这条说明，不只是“页面某处出现了这句话”。

409这条让保存抛出带 `current` 的冲突，服务器上的P004已被别人改成9：

```jsx
test("409 冲突提示服务器上的库存并保留草稿，载入最新后才保存", async () => {
  const repository = freshRepository();
  const current = { ...seed[3], stock: 9, version: 2 };
  vi.spyOn(repository, "save").mockRejectedValueOnce(new ApiError(409, { code: "CONFLICT", message: "版本已变化", current }));
  const { user, form } = await openEditor(repository, "P004");
  const stock = within(form).getByLabelText("库存", { exact: true });
  await user.clear(stock); await user.type(stock, "8");
  await user.click(within(form).getByRole("button", { name: "保存", exact: true }));
  expect(await within(form).findByText("保存冲突：服务器上的 P004 已被修改（库存 9）。草稿已保留，可载入最新后再保存。")).toBeInTheDocument();
  expect(stock).toHaveValue("8");
  await user.click(within(form).getByRole("button", { name: "载入最新", exact: true }));
  expect(stock).toHaveValue("9");
  await user.clear(stock); await user.type(stock, "8");
  await user.click(within(form).getByRole("button", { name: "保存", exact: true }));
  await waitFor(() => expect(screen.queryByRole("form", { name: "商品编辑" })).not.toBeInTheDocument());
  expect(screen.getByText("库存 57 / 价值 2784300 分")).toBeInTheDocument();
});
```

预期：冲突提示带服务器上的库存9，草稿8保留；点「载入最新」后输入框变成9，再改成8保存才成功，汇总57。

失败后能不能重试，列表读取补一条：

```jsx
test("列表读取失败后显示原因，不停在加载中，重新读取恢复", async () => {
  const user = userEvent.setup();
  const repository = freshRepository();
  vi.spyOn(repository, "list").mockRejectedValueOnce(new ApiError(500, { code: "FAULT", message: "注入的故障：500" }));
  render(<App inventoryRepository={repository} />);
  expect(await screen.findByText(/^读取失败：HTTP 500：注入的故障：500/)).toBeInTheDocument();
  expect(screen.queryByText("正在加载库存")).not.toBeInTheDocument();
  await user.click(screen.getByRole("button", { name: "重新读取", exact: true }));
  expect(await screen.findAllByRole("article")).toHaveLength(6);
});
```

预期：页面说出失败原因，不停在“正在加载库存”；点一次「重新读取」回到六种商品。

详情和保存的失败重试不新增重复测试。打开已有 `tests/react/inventory.test.jsx`，找到“详情失败后点击重试恢复”：它只让repository.get首次拒绝，真实App、ProductDetail、Query以及后续repository读取都保留。第一次看到错误，点重试后读到P002/库存0；不能把两次读取都改成直接成功。

同文件的“提交失败后草稿保留，重试成功才更新列表和统计”要求草稿8保留、全量仍52，解除失败后才57。这几条都用mock repository加替身，测不到HTTP状态、`If-Match` 和数据有没有写进后端；这些交给第4节连真实后端的一条流程，不能把两者混成一条“网络测试”。

## 4. 浏览器冒烟串起最重要的一条交付路径

<a id="4-浏览器冒烟串起最重要的一条交付路径"></a>

RTL能等待每次事件完成，真实浏览器却可能在路由尚未提交时已经处理下一个按键。因此保留严格产物上的逐字键盘回归，不用整串fill代替它。

**先猜一猜：** 搜索框value直接来自URL，路由更新默认进入transition，逐字打P004一定完整吗？不一定；旧URL值可能把受控输入还原，变成 `4` 或 `P4` 等不完整文本。一次性填入P004反而可能通过。

在 `src/react/App.jsx` 顶部的App返回值里，只修改HashRouter开始标签，闭合标签不变：

```jsx
<HashRouter useTransitions={false}>
```

预期：路由位置同步提交，受控搜索值及时更新；刷新后仍从hash查询参数恢复。React的[transition不能控制文本输入](https://react.dev/reference/react/startTransition)，本项目六条商品选择同步导航；大型页面也可把输入草稿与延后结果拆开，当前不再增加第二份状态。Java顺序赋值直觉不等于React/路由更新的调度时机。

写入有没有真的到后端，只有真实浏览器加真实后端能回答。新建 `tests/e2e/api.spec.js`：

> 未运行验证：这条浏览器流程还没有在本课的工作区里运行。请按步骤自己尝试。

```js
import { test, expect } from "@playwright/test";
test("真实后端：保存 P004=8 后刷新仍是 8，总库存 57", async ({ page, request }) => {
  expect((await request.post("/api/_lab/reset")).status()).toBe(204);
  await page.goto("./");
  await expect(page.locator("#summary")).toHaveText("库存 52 / 价值 2634800 分");
  await page.getByRole("button", { name: "编辑 P004", exact: true }).click();
  const form = page.getByRole("form", { name: "商品编辑", exact: true });
  await form.getByLabel("库存", { exact: true }).fill("8");
  await form.getByRole("button", { name: "保存", exact: true }).click();
  await expect(form).toHaveCount(0);
  await page.reload();
  await expect(page.locator('article[data-id="P004"]')).toContainText("库存 8 件");
  await expect(page.locator("#summary")).toHaveText("库存 57 / 价值 2784300 分");
  const saved = await request.get("/api/products/P004");
  expect(await saved.json()).toMatchObject({ id: "P004", stock: 8, version: 2 });
});
```

预期：先恢复固定数据，保存后刷新仍是8和57，后端读回的P004是version 2。刷新这一步排除了“只是Query缓存里变了”；最后一次 `request.get` 直接问后端，排除了“只是页面显示变了”。这里用 `fill` 没问题：它测的是持久化，逐字输入的风险已由上面的回归负责。

工作区运行 `npm run lab -- check C47`。它运行新增回归、已有必要行为、严格浏览器和这条真实后端流程；包括逐字输入、P004取消/空白/Enter保存、刷新、详情失败重试及缺文件404。检查器用临时数据文件启动后端和带 `/api` 代理的严格预览，不改你的 `.lab/server/products.json`。默认8068端口，先结束手工预览。

## 常见错误与调试

<a id="错误-1快照报错了好数据却已经没了"></a>

**现象**：非法库存被拒绝，旧快照却已经变坏。为复现，在 `src/services/storage.js` 的saveProducts函数内，**在 `const text = encodeSnapshot(products);` 之前**暂时插入：

```js
// 有问题的写法：校验之前已经写入外部存储
storage.setItem(key, JSON.stringify({ version: 1, products }));
```

**工具**：在工作区运行下面的最小回归；Sources也可在新增setItem和encodeSnapshot两行设断点：

```sh
node node_modules/vitest/vitest.mjs run --config tools/delivery.config.mjs tests/react/regression.test.jsx -t 非法保存
```

**证据**：throw断言仍通过，下一条原文比较失败；实际P004.stock是字符串 `"8"`，期望是旧记录中的数字3。**原因**：异常不会撤销刚才的setItem。**修复**：删掉新插入的行，恢复“encodeSnapshot先完成校验，之后才有任何存储写入”。**确认**：相同测试变绿，主键与backup整个Map相等，再运行check C47。

<a id="错误-2连续输入后搜索词少了一个字"></a>

连续输入的另一条证据是：删除useTransitions=false，生产浏览器期望P004却得到不完整文本；恢复后文本完整，StrictMode保留。测试失败应来自真实行为，不通过改整串fill或增加输入延迟来绕开。

- 先写失败后果，再选最小合适层级。
- 抛异常之后还要验证外部副作用，快照必须保住旧原文。
- RTL与真实键盘浏览器互补，等待条件而非固定时间。
- 后端错误在repository边界用替身测界面反应，持久化用一条真实后端流程测。
- 复用已有有效回归，手工补真实布局和操作可达性。
