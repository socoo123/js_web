## 1. 用 state 记住界面需要的值

React 每渲染一次，就重新调用一次组件函数，普通局部变量也随之重建。需要跨渲染保留的值叫 state，交给 React 保存。`useState` 返回本次的值和一个请求更新的 setter。

**记住：** `useState(product.stock)` 的参数只在第一次渲染时使用，之后 React 返回它保存的值。

所以 product 换了，这份 state 不会自动跟着换。`add` 复用 core 的 `updateStock` 算出下一库存，超出上限时保留原值。

## 2. 一次渲染的值是固定的

每次渲染拿到的 state 像一张快照：这次渲染里创建的函数，读到的始终是这张快照。调用 setter 只是请求下一次渲染，不会改手上的值。

## 3. 批处理与更新队列

React 把同一次事件里的更新先排进队列，事件结束后一起处理，这叫批处理。传值的意思是「把结果替换成这个值」，所以三次 `setStock(13)` 仍是 13。

新值依赖前一步结果时，传一个函数，例如 `setStock((previous) => previous + 1)`。这种函数叫 updater，React 处理队列时把前一步的结果交给它。

把对照卡右侧的 `restockThree` 放进组件，替换上一节的错误版本。

<Predict question="从 12 开始，这个混合队列处理完是几？本次事件里的 stock 是几？">

```jsx
setStock(stock + 1); // 替换为 13
setStock((previous) => previous + 3);
setStock(0); // 替换为 0
setStock((previous) => previous + 2);
```

<div slot="answer">

```text
队列：12 → 13 → 16 → 0 → 2
下一次页面：2
本次事件里的 stock：12
```

队列按顺序处理，替换和 updater 可以混用。日常递增统一写 updater，读代码的人不用手算。

</div>
</Predict>

updater 必须是纯函数：只根据参数算出返回值。开发时的检查模式 StrictMode 可能把它调用两次来暴露副作用，所以发请求、计数、弹通知都不能写在里面。

**Java 对照：** Java 的纯函数同样可以放心重复调用；React 正是依赖这一点来检查 updater。

## 4. 延迟补货要基于执行时的待更新值

定时回调捕获的是创建它的那次渲染。点击时库存是 12，稍后执行 `setStock(stock + 3)`，会把中途补到的库存直接替换掉。

updater 拿到的是定时器执行时队列里的待更新值，所以从中途补过的库存算起。闭包里的旧 stock 并没有被「刷新」，只是计算时不再用它。

如果业务要的恰好是点击那一刻的信息，比如把当时选中的商品交给盘点任务，就明确捕获它的 id。作用在哪个商品和数量怎样累计，是两个问题。

**Java 对照：** Java 的 lambda 只能捕获 effectively final 的局部变量，看到的同样是创建时的值；React 还多了一层渲染快照。

`onClick` 接收的是函数，点击时才执行。写成 `onClick={restockThree()}` 会在渲染时就调用它，造成重复更新。箭头函数也是函数值，写在 JSX 里不会提前运行。

`useState` 这类以 use 开头的 React 函数叫 Hook。Hook 必须写在组件顶层，每次渲染按相同顺序调用；不要放进 if、循环、事件回调，也不要放在提前 return 之后。

**Java 对照：** Java 按字段名找实例字段；React 按调用顺序找 state，顺序一变就会对错位置。

## 常见错误与调试

### 连续补三件只有 13

**现象**：刷新后是 12，点一次「连续补三件」只得到 13。

**工具**：React DevTools → Components，选中 StockActions 看 State。Sources 打开 StockActions.jsx，在处理函数第一句 setter 的行号上单击，设断点。

**证据**：

```text
停在第一句 setter：stock = 12
单步越过三句 setter：stock 仍是 12，三次参数都是 13
继续运行后，Components 里的 State：13
```

**原因**：三次请求都是用同一张快照算出的替换值，队列里没有累计。

**修复**：改成对照卡里的三个 updater。延迟回调同样用 updater，不用旧 stock 做替换。

**确认**：刷新后重做第 1 步，得到 15；再刷新，先点延迟补三件、再点立即补一件，先显示 13，三秒后显示 16。最后运行任务卡里的检查：

## 小结

- state 是每次渲染的快照，setter 请求下一次渲染。
- 同一事件里的更新排队处理：传值是替换，传函数按前一步结果计算。
- 延迟回调保留旧闭包；需要累加时用 updater。
- updater 保持纯粹，Hooks 在顶层按固定顺序调用。
