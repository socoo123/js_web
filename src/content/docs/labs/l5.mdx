## 目标 1：接上后端

**先读**：[C45 第 1 节：先确认失败的是哪一种资源](/js_web/07-project/c45-debug-delivery-checks/#1-先确认失败的是哪一种资源) · [C13 fetch 的响应分两步处理](/js_web/03-async-modules/c13-async-await-fetch/#2-fetch-的响应分两步处理) · [C32 mutation 与失效](/js_web/05-react/c32-tanstack-query-server-state/#5-mutation-与失效先写成功再更新读结果)

后端只监听本机 `127.0.0.1:8070`，数据存在工作区的 `.lab/server/products.json`。第一次启动时它从 `data/products.json` 生成这份文件，所以一开始就是固定数据；浏览器里原来的个人快照不受影响，切回 mock 模式时还在。

**1. 开两个终端，都在库存工作区执行。**

```sh
# 终端 A：后端，保持运行
npm run lab -- api
```

```text
库存后端：http://127.0.0.1:8070/api（数据 .lab/server/products.json；Ctrl+C 停止）
```

```sh
# 终端 B：前端
npm run lab -- start C45
npm run lab -- dev
```

**2. 写四个文件。** 方法名和返回形状与原来的 `inventory-repository.js` 一致，组件和测试因此不用改。

| 文件 | 要做什么 |
| --- | --- |
| `src/services/api-repository.js` | 导出 `ApiError`（带 `status`、`code`、`fields`、`current`）和 `createApiRepository({ baseUrl, fetch })`。`list`、`get`、`save`、`create`、`remove`、`restock` 与原 repository 同名同形，另加 `listPage(params)` 与 `reset()` |
| `src/services/data-source.js` | 按 `import.meta.env.VITE_DATA_SOURCE` 导出 `repository` 与 `dataSource`：`"api"` 是默认，`"mock"` 用原来的 `inventory-repository.js`，其他值直接抛错 |
| `src/react/InventoryProvider.jsx` | 默认 repository 改从 `data-source.js` 取；测试仍注入 `freshRepository()` |
| `vite.config.js` | 在配置对象里加 `server: { proxy: { "/api": "http://127.0.0.1:8070" } }` |

`api-repository.js` 的几条规则：

- `baseUrl` 默认取 `import.meta.env.VITE_API_BASE`，没设就是 `"/api"`。相对地址让浏览器只和页面所在的 8060 通信，由 Vite 代理转给 8070。
- 非 2xx 一律抛 `ApiError`，消息取错误体的 `error.message`。断网、CORS 这类没拿到响应的失败保留原来的 `TypeError: Failed to fetch`。
- `save` 发 `PATCH`，头里带 `If-Match: "<version>"`。version 用这个 repository 最近一次从服务器拿到的该商品的值，所以每个响应里的商品都要记下 version。
- `options.signal` 原样交给 `fetch`。`failNext(operation)`、`options.fail` 与 `options.delay` 改成调用 `POST /api/_lab/faults`，让模拟的失败也出现在 Network 与 api 终端。

完整参考解在本课完成后用 `npm run lab -- compare C45` 对照；接口细节见 [L5 后端接口](/js_web/labs/api/)。

**3. 确认接上了。**

| 看哪里 | 应该看到 |
| --- | --- |
| 页面 | 标题下有「数据源：本地后端 /api」；汇总为「库存 52 / 价值 2634800 分」；快照区只剩「恢复固定数据」按钮 |
| Network | `GET /api/products…` 状态 200，Request URL 以 `http://127.0.0.1:8060/api/` 开头（同源，经代理） |
| api 终端 | 同一请求对应一行，例如 `GET /api/products?page=1&pageSize=50 200 3ms` |
| 刷新验证 | 给 P001 补一件得到 13/53，api 终端出现 `POST /api/products/P001/restock 200`；刷新后仍是 13 |

最后点「恢复固定数据」回到 52。Network 的一行和 api 终端的一行，是整个 L5 排错的两头证据。

## 目标 2：全链路排错

**先读**：[C45 第 2 节：事件执行了，React 仍需要新的状态](/js_web/07-project/c45-debug-delivery-checks/#2-事件执行了react-仍需要新的状态) · [C45 常见错误](/js_web/07-project/c45-debug-delivery-checks/#补货点了数字一直停在-12)

先做 C45 的主错误：`App.restock` 直接改 Query 读到的商品。点 P001 的补货后，Network 与 api 终端都**没有** `POST /api/products/P001/restock`，刷新后仍是 12。恢复 `await dispatch(...)` 后重做同一操作，得到 13/53 且刷新仍在。

下面五个场景各制造一个故障。每个都从「恢复固定数据」开始，按「操作 → 证据 → 修复 → 复验」做，把证据写进 `notes/debug.md`。需要后端配合出错时用故障注入，在页面的 Console 里执行（经代理发给后端，[参数说明](/js_web/labs/api/#故障注入)）：

```js
// 例：让下一次 GET /api/products 返回 500
await fetch("/api/_lab/faults", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ method: "GET", path: "/api/products", status: 500 }),
});
```

注入的故障只生效指定次数（默认 1 次）；被它影响的请求在 api 终端的行尾带「注入故障」。「恢复固定数据」会同时清掉没用完的故障。

### 场景 1：直连 8070，被 CORS 拦下

**先读**：[C13 fetch 的响应分两步处理](/js_web/03-async-modules/c13-async-await-fetch/#2-fetch-的响应分两步处理)（同源与 CORS） · [C45 404、断网与错误正文分别判断](/js_web/07-project/c45-debug-delivery-checks/#404断网错误正文分别判断) · [MDN：CORS](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/CORS)

1. **操作**：Ctrl+C 停掉终端 B，改用 `VITE_API_BASE=http://127.0.0.1:8070/api npm run lab -- dev` 启动，刷新页面。
2. **证据**：页面显示「读取失败：Failed to fetch」。Console 报 CORS 错误：响应没有 `Access-Control-Allow-Origin`。Network 里请求发往 `http://127.0.0.1:8070`，状态是 CORS error。api 终端却有这次 `GET` 的 200 记录：后端已经回复，是浏览器不让脚本读。
3. **修复**：去掉 `VITE_API_BASE`，回到相对地址 `/api` 走 Vite 代理。不要改成 `mode: "no-cors"`，那样拿到的是读不出 JSON 的不透明响应。
4. **复验**：重启终端 B，Request URL 回到 8060，页面 6/52/2634800。对照实验：用 `LAB_API_CORS_ORIGIN=http://127.0.0.1:8060 npm run lab -- api` 重启后端后，直连也能读，说明放行权在服务器。做完改回默认启动方式。

### 场景 2：422 的字段错误要落到输入框

**先读**：[C25 名称、原因和下一步都要找得到](/js_web/05-react/c25-forms-validation-accessibility/#4-可访问性名称原因和下一步都要找得到) · [C30 HTTP 返回了，不等于商品加载成功](/js_web/05-react/c30-requests-races/#2-http-返回了不等于商品加载成功) · [MDN：422](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Reference/Status/422)

1. **操作**：注入 `{"method":"PATCH","path":"/api/products/P004","status":422,"body":{"error":{"code":"VALIDATION","message":"商品字段不合法","fields":{"priceCents":"价格必须是非负安全整数分"}}}}`，然后编辑 P004 并保存。前端校验与后端同源，正常输入很难触发 422，所以用注入模拟服务端拒绝。
2. **证据**：Network 有 `PATCH /api/products/P004` 422，Response 的 `error.fields.priceCents` 有消息；api 终端那一行带「注入故障」。故障版本只在表单底部显示一句笼统的失败，价格输入框旁没有提示。
3. **修复**：编辑器捕获 `ApiError`，把 `fields` 按字段名放到对应输入框（`priceCents` 对应价格），并让输入框带上错误说明；没有对应字段的消息放在表单底部。草稿保留。
4. **复验**：再注入一次，价格输入框旁出现「价格必须是非负安全整数分」，草稿仍是刚填的值；不注入时同样的保存成功。

### 场景 3：保存成功了，列表还是旧的

**先读**：[C32 mutation 与失效：先写成功，再更新读结果](/js_web/05-react/c32-tanstack-query-server-state/#5-mutation-与失效先写成功再更新读结果)

1. **操作**：在 `InventoryProvider.jsx` 的 mutation `onSuccess` 里暂时删掉失效列表的那一句，然后把 P004 编辑为 8 并保存。
2. **证据**：Network 有 `PATCH /api/products/P004` 200，Response 里 `stock` 已是 8、`version` 变成 2；但后面没有新的 `GET /api/products`，api 终端也只有 PATCH 那一行。列表仍显示 3、汇总仍 52；刷新后才是 8/57。
3. **修复**：恢复失效。保存、新建、删除、补货成功后失效 `["inventory"]` 前缀下的查询，列表与详情一起重新读取。
4. **复验**：同样的保存后，PATCH 后面紧跟一条 `GET /api/products…`，列表直接显示 8，汇总 57，P001 仍为 12。

### 场景 4：500 之后要能重试

**先读**：[C30 HTTP 返回了，不等于商品加载成功](/js_web/05-react/c30-requests-races/#2-http-返回了不等于商品加载成功) · [C32 重试与界面状态](/js_web/05-react/c32-tanstack-query-server-state/#4-重试与界面状态有旧结果时继续显示)

1. **操作**：用上面的 Console 片段注入一次 `GET /api/products` 500，然后刷新页面。
2. **证据**：Network 一条 500，Response 是 `{"error":{"code":"FAULT","message":"注入的故障：500"}}`；api 终端那一行带「注入故障」。故障版本的页面一直停在「正在加载库存」，或者报 `products.filter is not a function`：repository 把错误体当成了商品数组。
3. **修复**：请求函数先看 `response.ok`，非 2xx 读出错误体后抛 `ApiError`。Provider 在读取失败时显示「读取失败：…」和「重新读取」按钮。
4. **复验**：页面显示「读取失败：注入的故障：500」。故障只注入了一次，点「重新读取」后回到 6/52/2634800，api 终端多出一行 200。

### 场景 5：慢请求不能覆盖新选择

**先读**：[C30 后发先到：旧结果为什么覆盖新选择](/js_web/05-react/c30-requests-races/#3-后发先到旧结果为什么覆盖新选择) · [C32 query key 和缓存](/js_web/05-react/c32-tanstack-query-server-state/#3-query-key-和缓存先问是不是同一份数据)

1. **操作**：注入 `{"method":"GET","path":"/api/products/P001","delayMs":1500}`，打开 P001 详情，不等它出来就立刻打开 P002。
2. **证据**：Network 里 P001 的请求要约 1.5 秒，P002 很快返回。故障版本最后显示的是晚到的 P001。
3. **修复**：详情的 query key 带商品 id，`get(id, { signal })` 把 `signal` 交给 `fetch`。离开 P001 时它的请求被取消，Network 那一行显示 (canceled)。
4. **复验**：重做同一操作，最终显示「P002 无线鼠标：库存 0」，地址也是 P002。

做完五个场景，再按 C45 课文排查资源 404、存储原文、360px 布局和生产 source map。

## 目标 4：风险回归

**先读**：[C47 从失败后果开始写测试计划](/js_web/07-project/c47-project-testing-strategy/#1-从失败后果开始写测试计划) · [C47 请求替身放在哪里决定测到了什么](/js_web/07-project/c47-project-testing-strategy/#请求替身放在哪里决定测到了什么) · [C35 一条真实浏览器冒烟贯通静态路由](/js_web/05-react/c35-react-testing/#5-一条真实浏览器冒烟贯通静态路由)
